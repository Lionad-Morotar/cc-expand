## Problem Statement

Claude Code CLI 将 `MODEL_CONTEXT_WINDOW_DEFAULT` 硬编码为 200000 tokens。虽然底层模型（Claude Sonnet 4）支持 1M tokens，但 CLI 层面人为限制在 200k，导致长代码库重构、大规模文档处理时频繁触发上下文压缩，丢失关键信息。

环境变量 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 理论上可以覆盖，但代码中使用 `Math.min(window, envValue)` 逻辑，只能限制不能扩展。另一环境变量 `DISABLE_COMPACT` 需要配合 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 才能生效，但会完全关闭自动压缩机制。

**验证依据**: 在泄露源码 `zRefs/claude-code-source-*/` 中搜索 `MODEL_CONTEXT_WINDOW_DEFAULT` 可确认硬编码常量；`grep -a 'Math.min' ~/.npm/_npx/*/node_modules/@anthropic-ai/claude-code-darwin-arm64/claude` 验证了 `Math.min` 限制逻辑。

## Demand Evidence

- **直接用户**: 用户身边已有数人在使用手动分发的 patch 脚本
- **社区讨论**: Reddit r/ClaudeAI 大量关于 200k 限制的讨论帖，开发者普遍抱怨长会话被截断
- **竞品验证**: `janhlj/claude-code-max-context-patch` 在 GitHub 上存在，证明需求真实，但其方案（patch cli.js）有局限性
- **时间窗口**: 用户判断官方原生支持可能在 1 个月内到来，窗口期紧迫

## Status Quo

当前工作流程：

1. Claude Code 更新后，用户手动下载新二进制
2. 使用 `patch-claude-context.js` 脚本在二进制中搜索已知的字节模式
3. 将 `200000` 原地替换为目标值（如 `256000`）
4. `codesign --sign - --force --deep` 自签名
5. 通过 zsh 函数 `c 250` 启动补丁版本

痛点：
- **版本更新 = 手动重定位**: Claude Code 每次更新，JS 打包器生成新的变量名（如 `Aj8` → `zJ8` → `Lf8`），需要手动重新定位
- **分发困难**: 脚本通过社交工具手动传播，无版本管理
- **验证缺失**: 没有简单方式确认 patch 是否成功应用
- **门槛高**: 需要理解二进制结构、自签名、zsh 配置
- **无回滚**: patch 后若 Claude Code 崩溃，无法快速恢复原版

## Patch 后验证流程

每次 patch 后必须执行：

```bash
# 1. 字符串替换验证
grep -a 'Lf8=256000' patched-binary >/dev/null || exit 1

# 2. 二进制可执行验证
./patched-binary --version >/dev/null 2>&1 || exit 1

# 3. 自签名验证 (macOS)
codesign --verify --deep patched-binary >/dev/null 2>&1 || exit 1

# 4. 上下文窗口验证 (可选 smoke test)
# 启动 Claude Code 后执行 /context 检查显示值是否为 256k
```

**验证失败处理**: 如任一步骤失败，自动从 backups/ 恢复原始二进制，向用户报告具体失败步骤。

## Patch 可靠性数据

基于已有脚本的历史验证（3 个版本）：

| 版本 | 常量名变化 | Patch 成功率 | 备注 |
|------|-----------|-------------|------|
| v2.1.161 | `Aj8` → `zJ8` | 100% | 变量名改变，搜索模式需更新 |
| v2.1.162 | `zJ8` → `Lf8` | 100% | 同上 |
| v2.1.163+ | `Lf8` 稳定 | 100% | 当前稳定模式 |

**风险**: 若打包器将字符串字面量改为内联数字或压缩掉变量名，搜索模式将失效。需要设计 fallback：多模式匹配 + 启发式搜索（`grep -ao '[A-Za-z0-9_]*=200000'` 动态发现）。

## Target User & Narrowest Wedge

**目标用户**: 每天使用 Claude Code 处理大型代码库的高级开发者，熟悉终端操作，对 200k 限制感到沮丧。

**最小可交付（Wedge）**: 一个 `npm install -g cc-expand` 即可使用的交互式 CLI，自动发现 Claude Code 安装位置，一键 patch 并生成可直接启动的补丁二进制。

**用户日常启动流程**:
```
# Patch 后，用户有两种选择：
1. cc-expand run 250          # 通过 cc-expand 启动补丁版本（推荐，版本守护在此路径生效）
2. claude --context 250       # 原生命令（如果 cc-expand 创建了 shim/alias）

# v0.1.0 阶段：用户明确使用 `cc-expand run <tokens>` 启动
# v0.2.0+ 阶段：可选安装 shell alias `claude` → `cc-expand run`，透明替换
```

## Constraints

- 时间窗口约 1 个月（用户主观判断，基于对 Anthropic 产品节奏的经验推测，非官方路线图）。窗口期结束后，如官方已支持原生大上下文，项目归档；如未支持，继续维护至官方支持为止
- 官方更新可能导致常量映射失效
- 需要 macOS codesign 自签名
- Patch 要求目标值与源值位数相同（6 位数字）—— 原因：执行原地字节替换（`buf.write(TARGET_STR, replaceAt)`），更长字符串会覆盖后续字节破坏数据结构；更短字符串会在数值后留下原数字的剩余字节
- 仅支持 Claude Code 打包的 Node.js 二进制（Mach-O/ELF），不支持源码安装
- Linux ELF 支持待验证——当前脚本仅在 macOS Mach-O 上测试过，ELF 格式理论上无 codesign 需求，但 `.rodata` 段可能只读，需测试 `mprotect` 或复制到可写段
- macOS codesign 失败排查：SIP 状态检查（`csrutil status`）、证书有效性（`security find-identity -v -p codesigning`）、错误码映射（`codesign --verify` 返回码）

## Premises

1. 二进制 patch 方案比竞品（cli.js patch）更有价值——更底层、跨平台、不受 JS 文件更新影响
2. 1 个月窗口期内完成并推广仍能获得 GitHub 流量和潜在赞助者
3. 版本守护（自动检测更新并重打 patch）是用户最愿意为之付费/赞助的核心功能
4. macOS + Linux 优先于 Windows，Claude Code 核心用户群以 macOS 为主

## Landscape Findings

- **Layer 1（已知）**: Claude Code 200k 限制是社区共识痛点
- **Layer 2（搜索）**: 存在竞品 `janhlj/claude-code-max-context-patch`（Windows-only，patch cli.js），但功能范围和用户体验均有限
- **Layer 3（洞察）**: 竞品未解决的核心问题——版本更新后的自动化。这是 cc-expand 的差异化机会

**EUREKA**: 竞品 patch `cli.js`（会被 Claude Code 更新直接覆盖），而 cc-expand patch 的是打包后的二进制（更新会安装新二进制，但旧二进制不受影响）。这意味着版本守护的逻辑不同：竞品需要在每次更新后重新 patch `cli.js`，而 cc-expand 可以维护多个版本的补丁二进制，按需切换。这是一个被忽视的优势。

## Approaches Considered

### Approach A: 开发者工具（Developer-first）
- Summary: CLI 为核心，暴露所有底层能力，版本守护通过 cron/systemd 实现，常量映射支持社区 PR 更新
- Effort: M（1 周）
- Risk: Low
- Pros: 最符合用户群体，社区 PR 更新常量映射 = 免费的版本适配劳动力，代码最少
- Cons: 非开发者用户无法使用，推广天花板低，GitHub 上不够"惊艳"
- Reuses: 现有 `patch-claude-context.js` 脚本可直接迁移

### Approach B: UX 优先 CLI（推荐）
- Summary: 交互式 TUI 向导（使用 `ink` 或 `@inquirer/prompts`），自动发现 Claude Code 安装位置，一键 patch，带进度条和状态面板，版本守护内置
- Effort: L（1.5-2 周，含 @inquirer/prompts 学习成本 4-8h）
- Risk: Med
- Pros: 门槛最低，TUI 截图在 README 里很吸睛，最适合"吃 GitHub 流量"策略，版本守护解决最大痛点
- Cons: TUI 开发有学习成本，自动化发现安装位置在各平台上有 edge case
- Reuses: 现有 patch 脚本作为 core 包，CLI 层做封装

### Approach C: 平台化（未来可能性，当前不投入）
- Summary: 在线常量映射数据库 + 赞助提前获取。因需要后端且 2-3 周超出窗口期，**当前阶段不投入**。如官方未在 3 个月内支持，可 revisit。
- Effort: XL（2-3 周）
- Risk: High

## Recommended Approach

**Approach B（UX 优先 CLI）** with Approach A 的核心作为底层。

理由：
1. 最契合"1 个月窗口期 + 吃 GitHub 流量"的目标
2. TUI 截图是 GitHub 上最有效的营销工具
3. 版本守护解决当前最大痛点
4. 底层仍保留完整的开发者 API，未来可扩展为平台

## Open Questions（已决策）

1. ✅ **版本守护触发机制**: 选择文件系统 watcher（`chokidar` 监控 NPX 缓存目录），而非 cron。原因：更即时，用户更新后立即提示；cron 有延迟且需要常驻进程。
2. ✅ **TUI 框架**: 选择 `@inquirer/prompts`（轻量、学习成本低、2 小时可出原型），放弃 `ink`。原因：窗口期紧迫，ink 的 React 心智模型与 Node CLI 差异大，学习成本可能使总时间翻倍。
3. ✅ **常量映射更新**: 硬编码在 npm 包中，通过 `npm update` 获取新映射。原因：无后端依赖，窗口期内最可靠；如官方支持延迟，后期可扩展为远程拉取。
4. ✅ **Patch 回滚**: **必须支持**。Patch 前自动备份原始二进制到 `~/.cc-expand/backups/`，CLI 提供 `cc-expand restore` 命令。
5. ❌ **赞助入口**: v0.1.0 不实现。移至 v1.0 路线图。当前仅 README 放 GitHub Sponsors badge。

**维护策略**: 每次 Claude Code 更新后，通过 `grep -a` 动态发现新常量 → 验证 → PR 更新映射文件 → 发布 patch 版本。

## 版本守护架构

```
~/.cc-expand/
├── backups/
│   └── claude-v2.1.163-original      # 原始二进制备份
├── patches/
│   └── claude-v2.1.163-256k          # 补丁二进制
├── config.json                        # 用户配置（目标 tokens、自动 patch）
└── versions.json                      # 已知的版本→常量映射索引

NPX 缓存目录（被 watcher 监控）
└── ~/.npm/_npx/<hash>/node_modules/@anthropic-ai/claude-code-darwin-arm64/claude
    └── chokidar 检测到修改 → 对比版本号 → 提示用户重新 patch
```

**启动拦截**: 通过 `cc-expand run 250` 命令启动，该命令查找对应版本的补丁二进制并执行，无需修改用户的 `claude` 命令。

**Watcher 策略（解决 NPX hash 目录问题）**:
1. **初始发现**: `cc-expand` 首次运行时扫描 `~/.npm/_npx/`，按修改时间找到最新的 `claude-code-darwin-arm64/claude`
2. **监控范围**: 递归监控 `~/.npm/_npx/` 下所有 `claude-code-*` 目录（使用 `chokidar` 的 `ignored` 选项排除 node_modules，减少事件量）
3. **版本比对**: watcher 触发时，扫描所有 `claude-code-*` 目录，找到最新的二进制，提取其版本号
4. **增量检测**: 如果新版本号不在 `versions.json` 的已 patch 列表中，提示用户"发现新版本 X.X.X，是否重新 patch？"
5. **降级策略**: 如 chokidar 性能问题严重，回退到"每次 `cc-expand run` 启动前检查版本号"（零守护进程开销）
